# Migration: p5.js/p5play → q5.js/q5play

**Date:** 2026-08-02
**Status:** Implemented (see §8 for post-implementation findings from code review)
**Supersedes:** `01.p5play-v3-modernization-plan.md` (proposed groups/overlaps on p5play v3, never implemented — same concept now lands on q5play as part of this rewrite)
**Related:** `03.src-code-review.md` — several findings are carried into this migration (see §7); the rest are deferred to a future `05` reorg plan, done after this migration ships and is verified stable

## Why

p5play has been superseded by its own author's newer engine, q5play (q5.js WebGPU + Box2D v3 WASM). This migration moves the whole rendering/physics stack, and — since we're touching every entity's movement code anyway — adopts q5play's group/collision system for real gameplay events, which the current code fakes with hand-rolled `dist()` checks.

## Current state (baseline)

p5play usage in this codebase is minimal:
- `new ctx.Sprite(x, y, 20)` for position + rendering (`nova.mobile.js`)
- `sprite.remove()`, `sprite.visible`, `sprite.image`
- `p.kb.pressed(key)` for one-shot key detection (pause/help toggle)
- No physics, no collision groups, no `world` object ever touched — `planck` is a transitive peer dependency, never imported directly

Two independent distance-check mechanisms exist today, and they are **not the same kind of thing**:
- `touches()` (`nova.mobile.js:43`) — hard contact, `dist < 20`. Used for actual gameplay state changes: player-bites-human, zombie-bites-human, soldier-shoots-player, soldier-shoots-zombie, doctor-heals-zombie. **5 call sites**, all in `playloop()` (`nova-zombie-simulator.js`) plus one in `nova.doctor.js`.
- `proximityTo()` (`nova.mobile.js:47`) — soft-radius awareness, 50-200px depending on entity. Used purely for steering/avoidance AI in `zombie.move()`, `soldier.move()`, `doctor.move()`. Not a collision concept at all.

Movement is Perlin-noise wander (`Mobile.move()`), with direct `this.x`/`this.y` mutation, copied into `sprite.x`/`sprite.y` in `display()`. Player movement is arrow-key-driven, same direct-mutation pattern.

## Licensing note (must be understood before proceeding)

- `q5` (core renderer) is LGPL-3.0 — genuinely open, same terms as p5.js was.
- `q5play` itself ships under a custom **Creator License**, not OSI-approved:
  - Free for personal/commercial use, no source disclosure required.
  - Forbids CS-education use and military use.
  - **Requires an attribution element in the published game** — q5play injects a `#made-with-q5play` DOM element at runtime. This is not optional and should not be stripped.
  - Derivative works, if shared, must carry the same license terms.
- `q5play` pulls in `box2d3-wasm` as a hard dependency (physics engine), which we will now actually use (see below), so this is no longer dead weight.
- Maturity: q5play v4.3, ~2 months old npm history, 12 GitHub stars at time of writing. Minimal docs now in context7 (indexed 2026-08-01, thin compared to p5play's) — use as a first pass during implementation, but expect to fall back to reading `q5play.js`/`q5play.d.ts` source/README directly for anything not covered.

## Design decisions

### 1. Dependency swap

Remove: `p5`, `p5play`, `p5js-wrapper`, `planck`
Add: `q5`, `q5play`

Both `q5` and `q5play` are global-attach scripts (`window.Q5 = ...`, no ESM exports) — same side-effect import shape as today:

```js
await import('q5')      // sets window.Q5
await import('q5play')  // requires globalThis.Q5 or globalThis.p5 to exist; attaches itself
```

`q5` bundles sound/font/image loading natively (`loadSound`, `loadFont`, `loadImage`, `createButton`, `createDiv` all confirmed present in q5 core), so the separate `p5js-wrapper/sound` import goes away entirely — one less dependency, not a replacement.

### 2. Bootstrap

`new p5(p => {...})` → `new Q5(q => {...})`. Same instance-mode constructor shape (`Q5(scope, parent, renderer)`), no structural change to how `nova-zombie-simulator.js` is organized.

Canvas renderer defaults to Canvas2D (`c2d`) unless WebGPU is explicitly requested — we will **not** opt into WebGPU. No reason to take on WebGPU browser-support risk (Safari/older browsers) for a 2D top-down game with no rendering bottleneck.

### 3. Movement: kinematic bodies, velocity-driven

Every `Mobile` becomes a `kinematic`-type Sprite:
- Kinematic bodies move by velocity, ignore gravity/external forces, and are not pushed around by contact with other bodies — this matches the current "no physics feel" of the game exactly.
- `Mobile.move()` computes the same Perlin-noise delta as today, but sets `this.sprite.vel.x` / `this.sprite.vel.y` instead of mutating `this.x`/`this.y` directly.
- `Mobile.display()` reverses direction: it reads `this.x = this.sprite.x`, `this.y = this.sprite.y` **after** q5play's physics step has run, instead of writing sprite position from entity position.
- Screen-wrap logic (`if (this.x < 0) this.x = this.ctx.width` etc.) stays, now applied to the sprite's position directly (`this.sprite.x = ...`) when a wrap triggers, since sprite position is now authoritative.

This is the one structural change, and it's required: q5play's docs explicitly state that directly reassigning a sprite's position ("teleporting") breaks reliable collision/overlap detection. Since gameplay-critical collisions (`touches()`) are being replaced with real physics overlap events (see below), movement must go through velocity, not direct position writes.

Player movement (`nova.player.js:33`, arrow-key direct `this.x -= 5` etc.) converts the same way: arrow keys set `sprite.vel`, not `this.x` directly.

`proximityTo()`-based steering (avoid-soldier, seek-human, etc.) is **untouched** — it keeps reading `this.x`/`this.y` (now sourced from the synced-back sprite position) and keeps nudging via the noise-velocity path, not via q5play forces. This is steering AI, not a physics concept, and porting it to Box2D forces would be a bigger, riskier change than this project calls for.

### 4. Collision: groups + overlaps() for the 5 real contact events

`touches()` call sites map to q5play groups:

| Call site (today) | Groups | q5play replacement |
|---|---|---|
| `player.touches(human)` → convert to zombie | player (single sprite), `humans` group | `player.overlaps(humans, (p, h) => {...})` |
| `zombie.touches(human)` → convert to zombie | `zombies`, `humans` | `zombies.overlaps(humans, (z, h) => {...})` |
| `soldier.touches(player)` → kill player | `soldiers`, player | `soldiers.overlaps(player, (s, p) => {...})` |
| `soldier.touches(zombie)` → kill zombie | `soldiers`, `zombies` | `soldiers.overlaps(zombies, (s, z) => {...})` |
| `doctor.touches(zombie)` → heal to human | `doctors`, `zombies` | `doctors.overlaps(zombies, (d, z) => {...})` |

Each of `params.humans`/`zombies`/`doctors`/`soldiers` becomes a q5play `Group` instead of a plain array. Entities are still tracked as JS instances (`Human`, `Zombie`, etc.) — the group is what the underlying `Sprite` belongs to, giving us `group.overlaps()` for free instead of nested `for` loops with `dist()`.

`resetLevel()`'s current pattern (`objs.forEach(o => o.sprite.remove())`, splice/push between arrays) stays conceptually the same; `sprite.remove()` still exists in q5play (confirmed in source — removing a sprite removes it from all its groups).

### 5. Input

`p.kb.pressed('p')` (one-shot key-down detection, used for pause/help toggle) → q5play's `kb.presses('p')`. Same semantics (fires once on the frame the key goes down), different name — q5play's convention is `presses`/`pressing`/`released` rather than p5play's `pressed`.

### 6. Attribution / DOM

q5play injects a `#made-with-q5play` element into the page at runtime (license requirement). Needs a `css/style.css` rule so it doesn't fight the centered-canvas layout from the recent centering commit (`7c13f74`). Not to be removed or hidden in a way that defeats its purpose.

**Correction (found during Task 9 implementation, reading `q5play.js` directly):** this assumption was wrong on two counts. First, `Q5Play.splashScreen()` (`q5play.js:330`) is a full-screen, self-contained, self-removing splash (`position:absolute; width:100%; height:100%; z-index:1000`, inline-styled) shown once for ~3 seconds on load, not a persistent corner badge coexisting with the game layout — it needs no CSS accommodation since it's fully self-styled and deletes its own DOM node afterward. Second, it's gated by hostname (`q5play.js:~7195`): explicitly skipped on `localhost`/`127.0.0.1` and a long allowlist of coding-playground domains (CodePen, Glitch, StackBlitz, JSFiddle, the p5.js editor, etc.), only firing in the `default:` branch — i.e., real production domains, which includes the eventual GH Pages deploy. This is why it never appeared during any local dev-server testing. No `css/style.css` change is needed for this task; verified via source reading only, since the behavior can't be triggered on `localhost` to confirm visually.

### 7. Carried-in fixes from `03.src-code-review.md`

The physics/rendering rewrite already touches every file `03` flagged. Fixing these in-place avoids editing the same lines twice, and in one case (#8) the migration makes the existing problem worse if left alone. Findings from `03` folded in here:

- **#2 human double-movement bug** (`nova.human.js:10-16`) — `move()` calls `super.move()` then repeats the same noise-offset math inline, doubling wander speed. Delete the duplicate block; this file is being rewritten for velocity-driven movement anyway.
- **#4 killed-zombie leak** (`nova.zombie.js`, `Zombie.kill()`) — flags `killed=true` but never splices out of `params.zombies`. Fix goes directly in the new `soldiers.overlaps(zombies, ...)` callback (§4): splice on kill, same pattern as the other transitions.
- **#5 redundant re-randomization** (`nova.soldier.js:8-9`, `nova.doctor.js:7-8`) — constructors re-randomize x/y right after `super()` already did it. Delete; these constructors are being touched anyway for kinematic Sprite setup.
- **#6 `resetLevel()` builds `gameObjs` twice** (`nova-zombie-simulator.js:80,101`) — first assignment is dead. Drops out naturally once `gameObjs` becomes group references instead of arrays.
- **#3 duplicated steer/wrap logic** — screen-wrap duplicated across `Mobile`/`Human`/`Player`; steer-toward/away angle math near-identical across `Zombie`/`Soldier`/`Doctor`. Since `Mobile.move()`/`display()` are being rewritten for velocity (§3) regardless, pull wrap into `Mobile` only (reached via `super.move()`), and extract `Mobile.steerToward(target, speed)` / `steerAway(target, speed)` for the `proximityTo()`-driven AI to share.
- **#8 HELP screen instantiates real entities** (`displayHelp()`) — spins up real `Human`/`Soldier`/`Zombie`/`Doctor`/`Player` instances just to draw a static legend. Under the old engine that's a wasted plain Sprite; under q5play it's a wasted Box2D physics body per legend icon. Fix now, not later: draw the emoji glyphs directly with `q.text()` instead of constructing entities.
- **#9 / #10 library underuse, O(n⁴) collision loops** — this is just a description of the problem §4 (groups + `overlaps()`) solves. Not additional scope.
- **#11 dead file `single_sketch.js`** — confirmed orphaned, not referenced anywhere. Delete during this pass since we're already touching every other file.

**Deferred to a future `05` reorg plan** (organizational, no coupling to the engine swap — bundling them in would grow the diff on an already-risky migration for no shared-seam benefit):
- **#1 god file split** (`nova-zombie-simulator.js` → `gameState.js` / `collisions.js` / `screens.js` / `sound.js`) — easier after this migration anyway, since collision logic will already be reshaped into `group.overlaps()` callbacks with cleaner seams to cut along.
- **#7 magic numbers / `config.js`** — proximity thresholds, steer speeds, timers, sprite size. Orthogonal to the physics/rendering stack.

## Testing strategy

No automated test suite exists in this project (per `CLAUDE.md`) — validation is a manual playtest checklist:

- [ ] All 5 overlap events fire correctly (human→zombie via player, human→zombie via zombie contact, player death via soldier, zombie death via soldier, zombie→human via doctor heal)
- [ ] Wander movement looks/feels the same as before (noise-driven, not physics-jittery)
- [ ] Screen-wrap still works correctly for all entity types with velocity-driven kinematic sprites
- [ ] Player arrow-key movement feels the same (no physics lag/drift introduced by velocity conversion)
- [ ] HELP screen's ad-hoc preview sprites (`displayHelp()`, entities created outside the group system) still render correctly
- [ ] PAUSED / GAME_OVER / ATTRACT screens unaffected (no group/physics involvement there)
- [ ] `#made-with-q5play` attribution element doesn't break canvas centering
- [ ] Round-over/level-reset (`resetLevel()`) correctly clears and recreates groups each level
- [ ] Humans wander at normal (single) speed, not the pre-fix doubled rate
- [ ] Killed zombies (tombstone state) are actually removed from the zombies group/array, not accumulating over a play session
- [ ] `npm run build` / `npm run deploy` still produce a working GH Pages bundle (WASM asset for Box2D needs to be reachable at the deployed base path — flag as a risk to verify explicitly, since GH Pages deploy uses a non-root base path)

## Risks

- **Library maturity**: q5play is ~2 months old on npm, small community, only thinly indexed in context7 (as of 2026-08-01). Implementation should check context7 first but expect to read `q5play.js`/`q5play.d.ts` source directly for gaps, and budget extra time for API surprises.
- **Box2D WASM + GH Pages base path**: the deploy script sets `DEPLOY_ENV=GH_PAGES` for a non-root base path; Box2D's WASM binary is loaded via `import.meta.resolve('box2d3-wasm')` at runtime — needs explicit verification that this resolves correctly under Vite's build output and the GH Pages subpath, not just under `npm run dev`.
- **Velocity conversion changes feel**: converting direct position writes to velocity-driven kinematic movement is the single riskiest behavioral change here. Perlin-noise deltas are small per-frame, so it should be near-invisible, but needs a side-by-side playtest against current `main` to confirm no drift/lag artifact.

## 8. Post-implementation findings (code review, 2026-08-05)

Migration implemented across 20 commits; build verified clean and gameplay verified working in a live `npm run preview` browser session (humans wander, player spawns, no console errors). Two things the original risk assessment above didn't anticipate:

- **Box2D WASM is not bundled by Vite — it's fetched live from `https://q5play.org`**. `import.meta.resolve("box2d3-wasm")` survives untouched into the production bundle; confirmed via network tab that `Box2D.deluxe.{mjs,wasm}` load from `q5play.org` at runtime, not from `dist/`. This actually *resolves* the GH Pages base-path risk noted above (it's an absolute external URL, not a relative build asset) but introduces an undocumented single point of failure: the game cannot load — anywhere, including a from-source build — if `q5play.org` is unreachable. Not a blocker, but should be called out as a known dependency, not discovered by accident.
- **`SharedArrayBuffer usage is restricted to cross-origin isolated sites`** appears as a Chrome DevTools issue (not a thrown error) on every load. Local `vite preview` has no COOP/COEP headers and the game still ran fine, so this looks like a non-fatal fallback path in q5play/Box2D — but GH Pages also doesn't set those headers, and that combination hasn't actually been exercised. Verify against the deployed GH Pages URL specifically, not just local preview, before considering the WASM risk item above fully closed.
